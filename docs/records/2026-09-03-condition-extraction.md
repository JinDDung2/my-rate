# 우대조건 AI 추출 파이프라인 (§8 AI 파이프라인 명세)

## Goal

`spcl_cnd` 원문(비정형) → `SpecialCondition[]`(정형) 배치 추출 파이프라인을 구현하고,
`data/products.json` 전 건을 사람이 눈으로 검수해 `reviewed: true`로 만든다.
(REALRATE\_기능명세서.md §8, docs/github-issues/09-ai-extraction-pipeline.md)

## 구현

- `scripts/lib/types.ts` — `ConditionCode`/`SpecialCondition`/`RateOption`/`Product` (스펙 §6 그대로).
- `scripts/lib/pipeline.ts` — 검증 규칙을 코드로 강제하는 순수 함수:
  - `filterValidEvidence`: evidence가 원문 부분 문자열 아니면 폐기 (공백 정규화 후 비교).
  - `computeGapBp` / `pickRepresentativeOption`: 상품에 옵션(만기)이 여러 개일 때
    **우대갭이 가장 큰 옵션**을 대표값 G로 사용 (동률이면 가입기간이 긴 쪽).
    스펙은 "기본금리/최고우대금리"를 단수로 가정하지만 실제 공시는 만기별로 갈리므로,
    가장 관대한 기준을 써서 만기 차이로 인한 오탐(false low-confidence)을 줄였다 — **가정**.
  - `applyConfidenceRule`: Σ rateBp > G(bp)면 전부 `confidence: 'low'` + 수동 검수 큐.
  - `computeUnexplainedBp`: `max(0, G - Σ rateBp)`.
- `scripts/extract-conditions.ts` — 실제 Claude API 배치 호출 스크립트
  (`claude-opus-5`, `output_config.format: json_schema`로 구조화 출력, 파싱 실패 1회 재시도).
  `ANTHROPIC_API_KEY` 필요 — 이번 세션 환경에는 키가 없어 실행하지 못했다.
- `scripts/build-products.ts` — 원문 + 추출 결과 → 검증 통과 → `data/products.json`
  (`reviewed: false`로 시작).
- `scripts/mark-reviewed.ts` / `scripts/check-reviewed.ts` — 검수 완료 기록 / 배포 빌드 가드
  (`npm run build`가 `check:reviewed`를 실행).

## 가정 — ANTHROPIC_API_KEY 부재 시 추출 방식

`.env`에 `ANTHROPIC_API_KEY`가 없어 `extract-conditions.ts`를 실제로 호출하지 못했다.
API 크레딧을 새로 쓰는 대신, 이번 세션에서 내(에이전트)가 43건 전체의 `spcl_cnd`를
스크립트와 동일한 프롬프트 규칙으로 직접 판독해 `data/raw/extracted.json`을 만들고,
`build-products.ts`(실제 코드, 실제 검증 규칙)로 통과시켰다. 이후 그 결과를 원문과
1:1 대조하며 전량 눈으로 검수했다. 스크립트 자체는 키가 있으면 그대로 재사용 가능한
상태로 남겨둔다.

## 검수 중 발견한 오추출 유형 (메모)

1. **Σ(개별 항목) > 공시 캡** — "9가지 중 6가지 선택"(KB내맘대로적금), "가산금리 최고
   1.30%"인데 개별 항목 합이 1.90%(신한 알.쏠 적금)처럼, 원문이 "택N" 구조인데 개별
   항목을 전부 나열하면 합이 캡을 넘는다. 검증 규칙(Σ>G → 전부 low + 수동 검수)이
   정확히 이 두 건을 잡아냈다 — **의도대로 동작**. 다만 이런 상품은 화면에서 "최대
   N개까지 체크 가능" 같은 별도 UI 처리가 필요해 보임(현재 스펙엔 없음).
2. **상호 배타적 대안(mutually exclusive alternatives)** — "①/② 중복 적용 불가"처럼
   명시된 경우(NH1934월복리적금 급여이체 vs 개인사업자실적) 더 큰 값 하나만 채택.
   명시 문구가 없어도 구조상 택1인 경우(제주은행 사이버우대매일부금의 3개 통장 중 1개,
   하나은행 주거래하나우대 vs 플러스우대)도 있어, 개별 항목 대신 대표 문구 1건으로
   합쳐 추출했다. **모델이 "택1"을 명시적 신호 없이도 스스로 알아채야 하는 경우가
   많아, 이 판단은 사람 검수 없이는 신뢰하기 어렵다.**
3. **가입기간(만기)별 차등 우대율** — 표준 조건 8종은 가입기간을 구분하지 않는데
   원문은 1/2/3년제별로 다른 bp를 명시하는 경우가 흔함(KB국민프리미엄적금,
   KB맑은하늘적금 등). 대표 옵션(최대 우대갭)의 기간에 맞는 bp만 채택했다 — 다른
   기간으로 가입하는 사용자에게는 실제보다 과다/과소 계상될 수 있음. **데이터
   모델을 조건×만기 매트릭스로 확장하지 않는 한 구조적 한계.**
4. **총량만 공시, 개별 조건 비공개** — "우대이율 최대 X%"만 있고 조건별 배분이
   전혀 없는 경우(부산은행 펫 적금·Big적금, 케이뱅크 궁금한 적금·코드K 자유적금·
   마이키즈 적금 등 8건). `rateBp:0` + `OTHER`로 처리해 갭 전량을 `unexplainedBp`로
   흘려보냈다 — F-09(미해석 우대폭 고지)가 실제로 필요한 대표 사례들.
5. **표준 8종에 없는 조건 유형** — "오픈뱅킹 타행계좌 등록"(우리은행, 아이엠뱅크,
   신한은행 등 3건 이상), "개인(신용)정보 동의"(마케팅 동의와는 다른 개념인데
   근접 코드가 없어 `MARKETING_AGREE`로 근사), "교차거래" 같은 은행권 공통 조건이
   8종 표준 코드에 매핑되지 않아 전부 `OTHER`로 빠진다. 다음 배치 전 표준 코드
   세트 확장을 검토할 만함.

## 후속: 실제 Claude API 배치 재실행 (같은 날, 키 등록 후)

사용자가 `.env`에 `ANTHROPIC_API_KEY`를 등록해 `npm run extract:conditions`를
`claude-opus-5`로 실제 실행했다. 43건 전부 1차 시도에서 성공(재시도 0건, 파싱 실패 0건).

### 비교 방법

기존 수동 판독본을 백업(`extracted.manual.json`)해두고, API 결과로
`data/raw/extracted.json`을 덮어쓴 뒤 `build-products.ts`로 재조립 →
원문과 1:1 다시 대조(자동 diff 아님, 43건 전부 재검수).

### 1차 결과 — 검증 규칙이 잡아낸 것

```
수동 검수 필요 (7건): 저탄소 실천 적금, 사이버우대매일부금, KB내맘대로적금,
신한 알.쏠 적금, NH1934월복리적금, NH고향사랑기부적금, 주거래하나 월복리적금
```

수동 판독본은 2건만 걸렸는데(KB내맘대로적금, 신한 알.쏠 적금 — 원래 구조적으로
"택N" 문제라 정상), API 단독 실행은 5건이 추가로 걸렸다. **전부 상호배타적
대안(mutually exclusive alternatives)을 모델이 별도 항목으로 중복 합산한 경우**였다:

| 상품                  | 문제                                                                                      |
| --------------------- | ----------------------------------------------------------------------------------------- |
| 저탄소 실천 적금      | "개인형"(0.5%p)과 "기업형"(0.4%p, 다른 고객군 요율)을 더해버림                            |
| 사이버우대매일부금    | "①②③ 중복적용 불가"인 3개 대안 중 2개를 별도 항목으로 나눠 합산                           |
| NH1934월복리적금      | "①/② 중복 적용 불가"라고 원문에 **명시**돼 있는데도 둘 다 추출                            |
| NH고향사랑기부적금    | 만 65세 이상 / 만 19~34세, 나이대별 배타적 조건을 둘 다 추출                              |
| 주거래하나 월복리적금 | "주거래하나우대"와 그 상위호환인 "주거래플러스우대"를 둘 다 추출(상위 하나로 흡수돼야 함) |

→ **오추출 유형 2번(상호 배타적 대안)이 사람이 옆에서 안 잡아주면 실제로
가장 흔하게 터지는 실패 유형임을 확인.** 모델은 "①/②" 같은 명시적 신호가 있어도
놓칠 수 있다 — 프롬프트에 상호배타 규칙을 강화하거나(예: "중복 불가/택1로
읽히는 항목은 가장 큰 값 하나만 추출"), 빌드 검증 규칙을 이 유형 전용으로
하나 더 추가하는 것을 다음 개선 과제로 남긴다.

### 추가로 발견해 수정한 것 (Σ 규칙에는 안 걸리지만 오추출인 것)

- **"불명 시 rateBp 0" 규칙 미준수**: 개별 조건을 전혀 특정할 수 없고 총량 캡만
  있는 경우(펫 적금, 부산이라 좋다 Big적금, Only One 주거래 우대적금, 궁금한 적금)에
  모델이 캡 값을 그대로 `rateBp`에 채워 넣었다. `OTHER`라 `myRate` 계산에는
  영향이 없지만, `unexplainedBp`가 부정확해져 F-09(미해석 우대폭 고지)가
  거짓으로 "우대갭을 다 설명했다"고 표시할 뻔했다 — 전부 `rateBp: 0`으로 정정.
- **체크박스 정의와 안 맞는 코드 배정**: KB맑은하늘적금의 "종이통장/종이서식
  줄이기 미션"을 `NON_FACE_TO_FACE`로(→ `APP_MISSION`으로 정정), NH내가Green초록세상적금의
  "통장미발급"·"대중교통이용"을 각각 `NON_FACE_TO_FACE`·`CARD_USAGE`로(→ 둘 다
  `OTHER`로 정정) 잘못 배정 — 체크박스 문구("비대면 가입", "카드 실적")와 실제
  조건의 의미가 달라 사용자를 오도할 수 있었다.
- **가입기간별 차등 우대율 대표값 불일치**: KB맑은하늘적금의 "대중교통 미션"에
  1년제 값(0.4%p)을 썼는데, 대표 옵션은 3년제(우대갭 기준)라 3년제 값(0.6%p)으로
  정정 — 안 그러면 실제로는 없는 미해석 우대폭 20bp가 화면에 표시될 뻔했다.

### 결론

`claude-opus-5` 단독 추출은 evidence 환각(부분 문자열 위반)은 0건으로 매우
안정적이었지만, **상호배타적 대안 처리와 "불명 시 0" 규칙은 사람 검수 없이는
신뢰할 수 없다** — 실질적 오류가 난 상품을 전부 세면 다음과 같다(중복 상품 제외,
`data/products.json`으로 재확인함):

| 오류 유형 | 건수 | 상품 |
| --- | --- | --- |
| 상호배타 중복합산 | 5건 | 저탄소 실천 적금, 사이버우대매일부금, NH1934월복리적금, NH고향사랑기부적금, 주거래하나 월복리적금 |
| rateBp:0 규칙 미준수 | 4건 | 펫 적금, 부산이라 좋다 Big적금, Only One 주거래 우대적금, 궁금한 적금 |
| 코드 오배정 + 대표값 불일치 | 1건 | KB맑은하늘적금 (두 이슈 겹침) |
| 코드 오배정 | 1건 | NH내가Green초록세상적금 |

→ **43건 중 11건(약 26%)**에서 실질적 오류. (이전 초안에는 "8건(약 19%)"으로
적혀 있었으나, 위 표처럼 상품을 하나하나 다시 세보니 근거가 맞지 않아 정정함.
참고로 "수동 검수 필요 (7건)"은 Σ rule이 기계적으로 플래그한 원본 개수로,
그중 2건(KB내맘대로적금, 신한 알.쏠 적금)은 구조적으로 정상이라 실질 오류가
아니다 — 11건과는 다른 지표이니 혼동하지 말 것.)

다음 배치부터는 시스템 프롬프트에 "①/② 중복 불가, 택1 등 상호배타 문구가
있으면 가장 큰 값 하나만 추출하고 나머지는 evidence에만 남겨라"와 "개별 조건을
전혀 특정할 수 없으면 반드시 rateBp:0"을 더 명시적으로 강조하는 것을 검토한다.

**같은 세션에서 바로 반영함** — `scripts/extract-conditions.ts`의
`SYSTEM_PROMPT` 규칙 1·3을 위 두 가지를 명시하도록 고쳤다(상호배타 대안은
최댓값 하나만, 총량 상한만 있고 개별 조건 불명 시 rateBp는 반드시 0). 다음
배치 실행부터 적용된다 — 이번에 만든 `data/products.json`은 수정 전 프롬프트
결과를 사람이 직접 고친 것이라 재실행 없이도 유효하다.

# AI 추출 검증 지표: Σ rule 플래그 vs 실질 오류

우대조건 추출 파이프라인(`scripts/extract-conditions.ts` → `build-products.ts`)의
결과를 이야기할 때 두 가지 다른 숫자가 나온다. 섞어 쓰면 안 된다.

## 두 지표

### 1. Σ rule 플래그 — 코드가 자동으로 세는 수

`build-products.ts`의 `applyConfidenceRule`이 계산한다.

```
Σ(개별 조건의 rateBp) > G(대표 옵션의 우대갭)
```

이 부등식이 참이면 `confidence: 'low'` + 수동 검수 큐에 넣는다. **이 규칙이
잡는 실패 패턴은 딱 하나** — "택N/상호배타 조건을 모델이 전부 개별 항목으로
나열해서 합이 공시 캡을 넘는" 경우다.

- 산술식 하나로만 판단하므로 **오탐이 있다**: 원문 자체가 "9가지 중 6가지
  선택" 같은 진짜 택N 구조라 합이 캡을 넘는 게 정상인 상품도 걸린다. 이 경우
  규칙은 "의도대로 동작"한 것이지 추출 오류가 아니다.
- 산술식 밖의 오류는 **구조적으로 못 잡는다**: 합계가 캡을 안 넘거나 정확히
  같으면 무조건 통과. 아래 "실질 오류"의 상당수가 여기 해당한다.

### 2. 실질 오류 — 사람이 원문과 1:1 대조해서 확정한 수

전 건(43건)의 추출 결과를 원문 `spcl_cnd`와 사람이 직접 대조해 확정한다.
Σ rule과 무관하게, "원문이 말하는 것과 추출 결과가 실제로 다른가"만 본다.
확인된 유형:

| 유형 | Σ rule로 탐지되나? |
| --- | --- |
| 상호배타 중복합산 (조건을 둘 다 추출) | O — 대부분 합이 캡을 넘어 걸림 |
| `rateBp:0` 규칙 미준수 (총량 캡만 있는데 캡값을 개별 항목에 채움) | X — 캡과 정확히 같아지므로 통과 |
| 체크박스 정의와 안 맞는 `ConditionCode` 배정 | X — 금액이 아니라 의미가 틀린 것이라 산술식과 무관 |
| 가입기간(만기)별 차등 우대율의 대표값 불일치 | X — 그럴듯한 다른 숫자로 치환된 것이라 합계 자체는 안 틀어짐 |

## 왜 숫자가 다른가

2026-09-03 배치([기록](../records/2026-09-03-condition-extraction.md)) 기준:

- Σ rule 플래그: **7건** (그중 2건은 오탐 — 원문이 원래 택N 구조라 정상)
- 실질 오류: **11건** (43건 중 약 26%)

11건 중 Σ rule로 잡히는 건 5건뿐이고, 나머지 6건(rateBp:0 위반 4건 + 코드
오배정 2건)은 산술적으로 아무 이상이 없어 자동 규칙이 원천적으로 탐지할 수
없는 유형이었다.

## 결론 / 이후 배치에 적용할 것

- **Σ rule 플래그 수를 "오류 건수"로 보고하지 않는다.** 이건 자동 검수 큐에
  들어간 건수일 뿐, 실제 오류율의 하한(lower bound)도 아니고 상한(upper bound)도
  아니다 — 오탐도 있고 누락도 있다.
- 실질 오류율을 알려면 전수 수동 대조가 필요하다. 이 파이프라인은 애초에
  "결과 30~50건 전량을 눈으로 검수. 자동화하지 말 것"이 DoD라 이 원칙과도
  맞는다.
- Σ rule 같은 자동 검증은 **검수 우선순위를 매기는 용도**로만 쓴다 (이 큐에
  걸린 건 먼저 본다). "이 규칙을 통과했으니 안전하다"는 결론으로 쓰지 않는다.
